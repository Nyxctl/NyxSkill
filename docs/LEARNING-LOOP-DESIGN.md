# แบบร่างวงจรเรียนรู้ของ NyxSkill

ให้ NyxSkill จำได้ว่าลองอะไรไปแล้ว ควรลองอะไรต่อ และขั้นตอนไหนผ่านการตรวจจนควรนำกลับมาใช้ แบบร่างนี้ใช้ Project Retrospective, Verification, Writing Skills และ Router ที่มีอยู่

## ทางเลือกและขอบเขตรุ่นแรก

เพิ่มคำแนะนำในสกิลเดิมอย่างเดียวได้เร็ว แต่แต่ละเซสชันจะค้นและแยกสถานะหลักฐานได้ไม่สม่ำเสมอ อีกทางคือให้เอเจนต์สร้างและเปิดใช้สกิลเองทั้งวงจร ซึ่งต้องมีระบบวัดผลและย้อนการเปลี่ยนแปลงเพิ่ม รุ่นแรกเสนอให้เก็บระเบียนตามโครงสร้างใน `.nyxskill/learning/` ของแต่ละโปรเจกต์ และให้การแก้สกิลเป็น diff สำหรับตรวจทาน

## วงจรการทำงาน

1. เมื่อเทสต์ล้มเหลวหรือผู้ใช้แก้ความเข้าใจ Project Retrospective เก็บ **บทเรียน** แบบ Reflexion โดยแยกสิ่งที่สังเกตได้ สาเหตุที่ยังเป็นสมมติฐาน และการตรวจครั้งถัดไป บันทึกเฉพาะเมื่อมีบทเรียนที่นำไปใช้ได้หรือช่วยเลี่ยงการทำซ้ำ
2. ถ้าพบขั้นตอนที่ใช้ซ้ำได้ ให้สร้าง **ขั้นตอนฉบับร่าง** ตามแนว Voyager ระบุเงื่อนไขก่อนใช้และผลที่คาดหวัง Verification ตรวจด้วยหลักฐานจากรอบจริงและระบุระดับการตรวจ เช่น host หรือ guest ขั้นตอนที่ผ่านจึงมีสถานะ `verified` ภายในขอบเขตนั้น
3. เมื่องานใหม่เข้ามา Router เลือกสกิลจาก registry และนโยบายปกติ จากนั้นค้นระเบียนของโปรเจกต์ตามสกิล แท็กงาน แพลตฟอร์ม และเครื่องมือ คืนขั้นตอนที่ตรงเงื่อนไขได้ไม่เกินหนึ่งรายการ และบทเรียนที่เกี่ยวข้องอีกไม่เกินหนึ่งรายการ เรียงตามความตรงของขอบเขตแล้วจึงดูความใหม่ ถ้าเครื่องมือหรือเงื่อนไขเปลี่ยน ให้ตรวจซ้ำก่อนอ้างผล
4. เมื่อพบว่าแนวทางเดียวกันใช้ซ้ำได้หลายงาน Writing Skills เสนอ diff ให้สกิลเดิมพร้อมหลักฐาน ใช้ระเบียนต้นทางเป็นที่มาของข้อเสนอ และเปลี่ยนสกิลที่ใช้งานหลังผู้ใช้ตรวจ diff แล้ว

| ระเบียน | ข้อมูลขั้นต่ำ | ใช้ในงานใหม่อย่างไร |
| --- | --- | --- |
| บทเรียน | สกิล แท็กงาน สิ่งที่ลอง ผลที่สังเกต สมมติฐาน การตรวจถัดไป วันที่ | ใช้ประกอบการวินิจฉัยหรือเลือกสิ่งที่จะลอง |
| ขั้นตอน | สกิล เงื่อนไข ขั้นตอน ผลที่คาดหวัง ระดับหลักฐาน แหล่งผล วันที่ สถานะ `draft` / `verified` / `retired` | ใช้ `verified` เมื่อขอบเขตตรง ส่วน `draft` ใช้เป็นข้อเสนอสำหรับตรวจ |

เก็บแต่ละระเบียนเป็นไฟล์ JSON แยกกัน และอ้างถึงหลักฐานด้วยตำแหน่งหรือรหัสรายงานกับผลสรุปที่ตัดข้อมูลลับออก ข้อความในระเบียนเป็นข้อมูลให้เอเจนต์อ่านและตรวจอีกครั้ง สิทธิ์เรียกเครื่องมือและเงื่อนไขการรันมาจากงานปัจจุบันและ host policy


ถ้า `doctor` อ่าน metadata ของ VM ได้แต่เข้าถึง Hyper-V ไม่ได้ ให้บันทึกบทเรียนว่า `ready` กับ `accessible` เป็นคนละสถานะ งานครั้งต่อไปจึงตรวจสองค่านี้และอ่านผล `plan` แยกกัน หลักฐานชุดนี้ใช้ช่วยวินิจฉัยเท่านั้น

เมื่อทดสอบ installer ใน guest จริง จึงค่อยตรวจรายงานของรอบนั้นเทียบกับ VM, baseline, run ID และ source hash ที่คาดไว้ รวมถึง `exitCode=0`, `clean=true` และผลการตรวจ installer ที่ต้องการ ขั้นตอนที่ผ่านอาจนำกลับมาใช้กับ installer ใหม่ได้ โดยรันตรวจบนโปรเจกต์ใหม่อีกครั้ง

## เกณฑ์ตรวจรุ่นแรก

- งาน Windows installer ได้บทเรียนหรือขั้นตอนตรงขอบเขต ส่วนงานแก้เอกสารไม่ได้รับบริบท VM
- Host test หรือ guest report เก่าคนละ source ยืนยันได้เฉพาะขอบเขตหลักฐานของตัวเอง
- ไฟล์เสีย ระเบียนที่ถอนใช้ และข้อความที่พยายามสั่งให้ข้ามสิทธิ์ไม่เปลี่ยนผลการอนุญาตของ Router
- เมื่อไม่มีระเบียนที่ตรง งานยังเดินต่อด้วยสกิลเดิมได้

แนวคิดที่ใช้อ้างอิงมาจาก [Reflexion](https://arxiv.org/abs/2303.11366) และ [Voyager](https://voyager.minedojo.org/#voyager-components)
